## 1. Как запустить:
Для запуска симуляции мультиплеерной игры запустите Play mode и нажмите кнопки Connect на двух дебаг панелях игроков, расположенных в нижних углах игрового экрана.

## 2. Архитектура:

Вся игра разделена на слои. `Domain` знает только правила морского боя. `Protocol` описывает сообщения между клиентом и сервером. `Server` хранит истинное состояние 
матча и принимает решения. `Networking` сериализует и доставляет сообщения, а также умеет имитировать задержку, потерю и дублирование пакетов. `Client` хранит только 
разрешённую игроку копию состояния. `Presentation` показывает эту копию в UI. `Runtime` создаёт все части и соединяет их на сцене.

Основной поток выглядит так: нажатие на клетку вызывает `BattleClient`, клиент отправляет `FireRequest` через `InProcessTransport`, `BattleServerTransportAdapter` 
передаёт запрос в `BattleServer`, сервер применяет правила и возвращает ответ. После реального изменения матча адаптер рассылает каждому клиенту персональный `MatchSnapshot`, 
клиенты обновляют `ClientState`, а UI перерисовывается по событию.

## 3. Протокол: какие сообщения ходят между клиентом и сервером;
Клиент и сервер не обращаются друг к другу напрямую. Обмен выполняется через transport layer сериализованными protocol messages.
### Client -> Server
- `JoinRequest` - первое подключение клиента к серверу. Сервер создаёт session, выдаёт `SessionToken` и назначает `PlayerSlot`.
- `ResumeRequest` - восстановление существующей session по ранее выданному `SessionToken`.
- `FireRequest` - попытка выполнить выстрел. Содержит `RequestId`, текущий `TurnId` и координату.
- `HeartbeatRequest` - application-level heartbeat для определения доступности сервера.
### Server -> Client
- `JoinResponse` - результат initial join, включая назначенную роль игрока и `SessionToken`.
- `FireResponse` - результат обработки выстрела: accepted/rejected и подтверждённый игровой результат.
- `MatchSnapshot` - персональная клиентская проекция authoritative состояния матча.
- `HeartbeatResponse` - ответ на heartbeat.
- `ErrorResponse` - ошибка для запросов, не имеющих собственного error representation.

## 4. Что происходит при разрыве и как обеспечены гарантии;
Transport поддерживает silent disconnect: доставка сообщений для выбранного клиента прекращается в обоих направлениях без transport disconnect event. 
Поэтому клиент не узнаёт о разрыве мгновенно. Потеря связи определяется на application level через heartbeat и отсутствие любых валидных серверных сообщений дольше заданного timeout. 
После этого клиент переходит в ConnectionLost и блокирует новые игровые действия.

При Connect доставка снова включается. Если у клиента уже есть SessionToken, новый игрок не создаётся: отправляется ResumeRequest, сервер находит существующую session и матч, 
после чего клиент получает свежий персональный MatchSnapshot. Snapshot применяется только если его StateVersion не старее уже подтверждённого локального состояния.
Recreate Client полностью уничтожает runtime клиента, его endpoint, heartbeat и локальное состояние, но SessionToken хранится отдельно. 
Новый runtime создаёт новый endpoint generation и возвращается в тот же матч через Resume.

Сетевые гарантии построены так, чтобы один пользовательский выстрел не мог примениться дважды, а клиент не мог откатиться к устаревшему состоянию. 
Каждый запрос имеет уникальный идентификатор, поэтому повторно доставленный выстрел распознаётся как уже обработанный и не меняет состояние сервера второй раз. 
Если ответ на выстрел потерялся, клиент может повторить тот же запрос и получить исходный результат. Номер хода не позволяет старому запросу выполниться уже в следующем ходе, 
а версия состояния не даёт более старому snapshot перезаписать новые данные на клиенте. Пока один выстрел ожидает подтверждения, второй независимый выстрел отправить нельзя.

## 5. Какие решения приняты (в том числе по неописанным деталям) и что упрощено;

Client 1 / Client 2 и Player 1 / Player 2 - разные сущности.
Client обозначает локальный runtime/UI slot.
Player назначается сервером:
- первый успешно выполнивший `JoinRequest` становится `Player 1`;
- второй - `Player 2`.
Поэтому Client 2 может стать Player 1, если подключится первым.

Play Mode запускается с двумя созданными, но не подключёнными клиентами.
Матч начинается только после второго успешного initial Join.

Клиент никогда не переключает ход самостоятельно.
Если активный игрок отключён, server timer продолжает работать и его ход заканчивается обычным timeout.

Disconnect не ставит матч на паузу.
Автоматическая победа соперника из-за disconnect не реализована.
Если игрок не возвращается, его session и матч сохраняются до завершения текущего server runtime. Оставшийся игрок может стрелять.

Restart Scene завершает текущий runtime и создаёт новый матч.
Восстановление server state после полного перезапуска сцены/сервера не входит в обязательный scope.

Использование Mirror/Photon/NGO или другого реального networking stack не реализовано так как противоречит одновременному выполнению требований:
- все в одном процессе;
- можно реконектить обоих игроков.
Пришлось бы либо вынести сервер из процесса в отдельный инстанс, либо ронять сервер когда игрок-хост вышел, после чего переподключиться не получится.

Приняты дополнительные правила для кораблей:

- корабли располагаются горизонтально или вертикально;
- корабли не пересекаются;
- корабли не соприкасаются.

Упрощения:
- игра не сохраняется после рестарта сцены;
- не реализованы экраны победы и поражения;
- нет настоящего сервера;
- нет системы подбора матчей: только два игрока, только одна игровая сессия;
- игроки не авторизуются иначе как "Player 1" и "Player 2";
- UI сгенерирован из атласа, полученного из одной итерации;
- Debug-сообщения выводятся в окна без скролла;
- нет VFX, музыки, SFX;
- нет экрана загрузки.
