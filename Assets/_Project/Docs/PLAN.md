# PLAN.md

## 1. Цель

Реализовать на Unity 6 минимальную сетевую игру «Морской бой» для двух игроков.

Базовая реализация работает в одном Unity-процессе: отдельный сервер, два независимых логических клиента и транспортная прослойка между ними. 
Клиенты не имеют прямого доступа к серверному состоянию и взаимодействуют с сервером только сериализованными сообщениями.

### 1.1. Правила игры

- Поле - 6x6.
- У каждого игрока корабли длиной 3, 2, 2 и 1 клетка.
- Корабли случайно расставляет сервер.
- Игроки стреляют строго по очереди.
- Попадание не даёт дополнительного хода.
- Результат выстрела: `miss`, `hit` или `sunk`.
- На ход даётся 15 секунд. Таймаут фиксирует сервер, после чего ход переходит сопернику.
- Побеждает игрок, первым потопивший все корабли соперника.
- Игрок видит своё поле и выстрелы соперника. На поле соперника видны только результаты собственных выстрелов.

## 2. Инструменты

- **Unity 6.3.10f1** - движок.
- **Codex** - основной AI-агент.
- **Unity CLI** - основной интерфейс автоматизации для AI-агента.
- **Coplay MCP** - дополнительный интерфейс для работы с Unity Editor, Scene Hierarchy, GameObject, компонентами, сценами и prefab.
- **UniTask** - основной инструмент для нового асинхронного кода.
- **Unity Test Framework** - EditMode-тесты.

Mirror и ParrelSync не входят в обязательную реализацию. При наличии времени Mirror может быть добавлен как альтернативная реализация transport layer.

Правила работы AI-агентов находятся в `AGENTS.md`.

## 3. Архитектура

Основные решения:

- `BattleServer` живёт независимо от клиентов и является единственным источником истины.
- `Client A` и `Client B` - отдельные runtime-клиенты со своим состоянием и UI.
- Client <-> Server взаимодействуют только через сериализуемые protocol messages.
- `InProcessTransport` эмулирует сеть и умеет delay, jitter, loss, duplicate и silent disconnect.
- `Domain` содержит чистые C#-правила и не зависит от Unity, UI или transport implementation.
- `RequestId` используется для идемпотентности пользовательской операции.
- `TurnId` идентифицирует конкретный ход.
- `StateVersion` защищает от старых и пришедших не по порядку состояний.
- `SessionToken` идентифицирует игрока независимо от текущего client runtime instance.
- После reconnect или client recreation сервер отправляет актуальный snapshot разрешённой клиенту проекции матча.
- Скрытые координаты кораблей соперника никогда не сериализуются клиенту.

## 4. План реализации

### 4.1. Подготовка проекта и конфигурации

1. Проверить версию Unity и подключить необходимые зависимости.
2. Создать одну стартовую сцену.
3. Создать `GameConfig : ScriptableObject`:
   - размер поля - 6x6;
   - корабли - 3, 2, 2, 1;
   - длительность хода - 15 секунд;
   - latency;
   - jitter;
   - loss rate;
   - duplicate rate;
   - heartbeat interval / timeout.
4. Создать asmdef/папки: `Domain`, `Protocol`, `Networking`, `Server`, `Client`, `Presentation`, `Tests`.
5. Зафиксировать направления зависимостей между слоями.

**Критерий завершения:** проект запускается из одной сцены, конфигурация вынесена в ScriptableObject, зависимости `Client -> Server` нет.

### 4.2. Domain и GameRules

Реализовать чистые C#-модели: `Board`, `Ship`, `Cell`, `PlayerState`, `MatchState`, `Position`, `ShotResult`, `GameRules`.

Реализовать и протестировать:

1. случайную серверную расстановку кораблей без пересечений и выхода за границы;
2. валидацию координат;
3. запрет повторного выстрела в обработанную клетку;
4. проверку текущего игрока;
5. `miss`, `hit`, `sunk`;
6. смену хода после любого принятого выстрела;
7. определение победителя.

**Критерий завершения:** матч можно полностью воспроизвести из EditMode-теста без сети и UI.

### 4.3. Сетевой протокол

Определить минимальный набор сериализуемых сообщений.

**Client -> Server**

- `JoinRequest`;
- `ResumeRequest`;
- `FireRequest`;
- `HeartbeatRequest`.

**Server -> Client**

- `JoinResponse`;
- `FireResponse`;
- `MatchSnapshot`;
- `HeartbeatResponse`;
- сообщение об отклонении/ошибке при необходимости.

Ключевые поля: `RequestId`, `TurnId`, `StateVersion`, `SessionToken`, server-side turn deadline.

Клиент передаёт только намерение выполнить действие. Результат выстрела, текущий ход и победитель определяются сервером.

**Критерий завершения:** клиент-серверный контракт описан независимо от transport implementation, UI и GameRules.

### 4.4. Серверный application layer

Реализовать:

- `BattleServer` / protocol handlers;
- `MatchService`;
- `SessionManager`;
- `RequestCache`;
- `SnapshotBuilder`;
- server clock / deadline processing.

Обработка `FireRequest`:

1. определить сессию и матч;
2. проверить `RequestId` в `RequestCache`;
3. проверить `TurnId` и право игрока на ход;
4. вызвать `GameRules`;
5. при изменении состояния увеличить `StateVersion`;
6. сохранить результат запроса;
7. вернуть `FireResponse`.

Повторный `RequestId` возвращает сохранённый ответ и не меняет `MatchState` повторно.

`SnapshotBuilder` создаёт отдельную проекцию для каждого игрока и исключает скрытые данные соперника.

**Критерий завершения:** сервер самостоятельно проводит матч и владеет полным authoritative state.

### 4.5. InProcessTransport

Реализовать транспортную прослойку между сервером и двумя клиентами.

Транспорт должен:

- сериализовать и десериализовать protocol messages;
- иметь отдельный endpoint для каждого клиента;
- доставлять сообщения Client -> Server и Server -> Client;
- поддерживать delay и jitter;
- поддерживать message loss;
- поддерживать message duplication;
- уметь полностью прекращать доставку конкретному клиенту без disconnect event;
- логировать `SENT`, `RECEIVED`, `DROPPED`, `DUPLICATED`;
- корректно очищать отложенные сообщения при уничтожении runtime instance или scene reload.

Игровая логика не должна знать, что transport работает внутри того же процесса.

**Критерий завершения:** сервер и клиенты могут обмениваться сообщениями только через transport API, включая нормальную и плохую сеть.

### 4.6. Два клиента и минимальный UI

В одной сцене показать два независимых клиентских блока одновременно.

Для каждого клиента реализовать:

- `BattleClient`;
- `ClientState`;
- `ClientConnectionMonitor`;
- UI собственного поля;
- UI поля соперника;
- статус хода;
- оставшееся время;
- `Pending`-состояние отправленного выстрела;
- индивидуальную debug panel.

При выстреле клиент:

1. проверяет только локальную возможность отправки;
2. создаёт `FireRequest` с новым `RequestId` и текущим `TurnId`;
3. показывает `Pending`;
4. блокирует второй независимый выстрел;
5. применяет только подтверждённый сервером результат.

Клиент хранит только разрешённую ему проекцию server state.

**Критерий завершения:** два клиента в одной сцене завершают полноценную партию через общий сервер на нормальной сети.

### 4.7. Серверный таймер хода

- Сервер хранит deadline текущего хода.
- Только сервер фиксирует истечение 15 секунд и переключает ход.
- Клиент отображает оставшееся время на основе серверного deadline.
- Просроченный `FireRequest` отклоняется сервером.
- Disconnect клиента не останавливает server-side clock.

**Критерий завершения:** authoritative turn не зависит от клиентского таймера или состояния соединения.

### 4.8. Debug panel и плохая сеть

Для каждого клиента:

- параметры latency / jitter / loss / duplicate;
- «Разорвать»;
- «Подключить»;
- «Пересоздать клиент»;
- включение/выключение network log.

Общий элемент:

- «Перезапустить сцену».

`Разорвать` прекращает доставку сообщений для выбранного клиента и не создаёт transport disconnect event.

**Критерий завершения:** плохую сеть можно воспроизвести вручную и увидеть судьбу сообщений в логе.

### 4.9. Reconnect и пересоздание клиента

1. Добавить application-level heartbeat.
2. При отсутствии серверных сообщений дольше заданного порога перевести клиента в `ConnectionLost`.
3. Заблокировать игровые действия потерявшего связь клиента.
4. После «Подключить» восстановить доставку и отправить `ResumeRequest`.
5. Сервер по `SessionToken` находит игрока и существующий матч.
6. Клиент получает свежий `MatchSnapshot`.
7. Snapshot принимается только если его версия не старее локальной.
8. «Пересоздать клиент» уничтожает весь runtime client instance и создаёт новый.
9. `SessionToken` хранится независимо от уничтожаемого client instance.
10. Новый клиент выполняет resume и возвращается в существующий матч.

`BattleServer`, `MatchState` и server-side session не уничтожаются при recreation любого клиента.

Можно последовательно пересоздать обоих клиентов, не потеряв игровой матч.

Если игрок не возвращается после разрыва, сервер сохраняет матч и сессию до окончания server runtime. Автоматическая победа по disconnect в обязательный scope не входит.

**Критерий завершения:** reconnect и recreation любого клиента не уничтожают матч.

### 4.10. Duplicate / loss / out-of-order

Проверить гарантии:

- потерянный `FireRequest` не меняет server state;
- потерянный `FireResponse` допускает retry с тем же `RequestId`;
- duplicate `FireRequest` возвращает cached response;
- duplicate response не применяется повторно;
- старая `StateVersion` не откатывает клиента;
- старый `TurnId` не позволяет действовать в новом ходе;
- быстрые повторные клики не создают два независимых выстрела.

**Критерий завершения:** одна пользовательская операция меняет server state максимум один раз, client state не откатывается назад.

### 4.11. EditMode-тесты

Правила игры:

- `miss / hit / sunk`;
- смена хода после попадания и промаха;
- победа после уничтожения последнего корабля;
- отклонение выстрела не в свой ход;
- валидность серверной расстановки.

Приоритетные сетевые сценарии:

1. `Duplicate FireRequest`.
2. `Lost FireResponse + retry`.
3. `Out-of-order StateVersion`.
4. `Reconnect + snapshot`.
5. `Fast double click / delayed response`.

Сетевые тесты должны быть детерминированными: фиксированные задержки или seed вместо неконтролируемой случайности.

**Критерий завершения:** основные сетевые гарантии проверяются автоматически.

### 4.12. Lifecycle и финальная проверка

- Проверить scene reload при сообщениях в пути.
- Безопасно отменять или игнорировать delayed tasks, timers и callbacks после уничтожения runtime instance.
- Очищать event/network subscriptions.
- Не обращаться к уничтоженным Unity objects.
- Проверить запуск проекта из чистого состояния.
- Пройти вручную полный матч, silent disconnect, reconnect и client recreation для обоих игроков.

**Критерий завершения:** scene reload не создаёт ошибок и старых callbacks.


**Критерий завершения:** репозиторий содержит все обязательные материалы для передачи.

## 6. Основные риски

| Риск | Снижение риска |
|---|---|
| Слишком сильная связанность server/client из-за одного процесса | Жёсткая зависимость через protocol + transport API, отсутствие прямых ссылок Client -> Server. |
| Повторный выстрел после потери ответа | `RequestId` + server-side `RequestCache`. |
| Старые сообщения откатывают клиента | Монотонный `StateVersion`. |
| Рассинхронизация после reconnect | Authoritative snapshot вместо воспроизведения пропущенной истории. |
| Утечка скрытых данных | `SnapshotBuilder` + отдельные клиентские DTO. |
| Клиентский таймер расходится с сервером | Клиентский таймер только отображает время, решения принимает server clock. |
| Delayed callbacks после recreation / scene reload | Cancellation, runtime generation checks, unsubscribe и очистка очередей. |
| Эмуляция сети случайно обходит сериализацию | Transport принимает и доставляет только сериализованный payload, а не ссылки на объекты сообщений. |
| Scope creep | Реальный networking stack, persistence и UI polish только после обязательного Definition of Done. |
| Невозможность миграции на реальный сетевой стек | Абстракция транспорта и независимость игровой логики от его реализации. |


## 7. Definition of Done

Обязательная часть готова, когда:

- проект открывается в Unity 6 и запускается из одной сцены;
- в одном процессе работают отдельный сервер и два независимых логических клиента;
- клиент-серверное взаимодействие происходит только сериализованными сообщениями через transport layer;
- сервер является единственным владельцем полного match state;
- корабли 3, 2, 2, 1 расставляются сервером;
- игроки ходят по очереди без бонусного хода за попадание;
- сервер определяет `miss / hit / sunk` и победителя;
- клиенты получают только разрешённую им информацию;
- server-side timeout переключает ход;
- pending-выстрел виден;
- быстрые клики не создают два выстрела;
- выстрел не в свой ход отклоняется сервером;
- доступны delay, jitter, loss, duplicate и silent disconnect;
- клиент самостоятельно обнаруживает silent disconnect;
- после «Подключить» состояние восстанавливается;
- можно пересоздать любого клиента и вернуть его в тот же матч;
- можно последовательно пересоздать обоих клиентов без потери server match state;
- duplicate/retry не повторяет выполненный выстрел;
- старые сообщения не откатывают client state;
- scene reload при сообщениях в пути не создаёт ошибок;
- есть EditMode-тесты правил и 3-5 рискованных сетевых сценариев.
